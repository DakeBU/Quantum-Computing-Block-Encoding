# Textbook checkpoint and stable-release frontier

The website's hierarchy is a reader projection of the retained source records,
not a new mathematical review or a new data release. The preview tag and all
historical artifacts remain unchanged. A functioning reader is an engineering
milestone; stable benchmark admission is a separate decision.

## Implemented checkpoint

- Five parts, twenty topics and one canonical page per retained native core ID.
- Separate mathematical and Lean companion paths using the existing site style.
- Assumptions before questions; hints, answers, rubrics and evidence folded.
- Exact shared-core/split contracts, UUID proposal checks and two collaborator goals.
- Three separately audited historical Lean reference warmups; no invented native aliases.
- Three native library-application views with source-blind decoding, a distinct
  semantic comparison and actual fixed-reference/axiom checks; same core IDs.
- Exact-predecessor withdrawals and separately reviewed additive repairs; affected
  explanatory summaries and semantic steps are repaired too, without changing
  question contracts or silently transferring historical acceptance.
- Standard site build/link checks and real desktop/mobile/theme/browser tests.
- Exact-content rejected/ambiguous records have reserved IDs and non-answer
  withdrawal notices; current search/downloads exclude their unapproved content.
  Stable review obligations keep the original scope instead of shrinking with
  the displayed question count.

## Remaining acceptance work

1. Review retained mathematical answers and rubrics in substantive bounded batches.
   Bind each review to the exact item digest, actual reviewer and inspected sources.
   Explicitly record defects or uncertainty; do not manufacture 213 accept labels.
2. Reconcile mathematical equivalences and specializations across native and legacy
   cohorts. Preserve lineage, review real split conflicts and do not sum unreconciled
   cohort counts into a globally distinct total.
3. Admit actual aligned native Lean views through independent semantic and exact-root
   kernel checks. Start with locally source-supported State Preparation/foundations;
   keep the source-only planned curriculum available as NL mathematics. Do not add
   hypotheses silently or call the three API warmups deep proof synthesis.
4. Recheck the generated reader and precise source/reference bindings after repairs.
   Publish and verify the actual source commit, not just a successful deployment API.
5. Define the exact stable release scope and evidence manifest only after those
   decisions. A global complete-library claim is not required and must not be implied.

The current `stable-check` fails closed on unfinished obligations. Its
shared-view gate reads exact native semantic and kernel evidence rather than
inferring acceptance from a directory name; passing that narrow first-batch
gate does not imply full formal coverage or deep proof synthesis.
Browser success must never stand in for mathematical/source review.

## Distinct later experimental gates

Untrusted generated Lean evaluation needs real isolation; the present environment
does not establish it. Real-model baselines remain unmeasured. Neither a hidden
evaluation claim, a universal PRM correctness claim nor a long GPU experiment is
part of this reader checkpoint. Formal acceptance, useful progress and faithful
natural-language explanation remain different labels.
